End to End Testing

End to End Testing#

What#

“End-to-end or (E2E) testing is a form of testing used to assert your entire application works as expected from start to finish or ‘end-to-end’.”
— Angular Docs

In RuFaS end-to-end testing, we have a specific set of output values saved which we expect to see from the model. When running end-to-end testing, outputs from the model are collected and compared to these saved values. If the values match, then end-to-end testing passes, otherwise it fails.

Key Terms#

  • Domain - a module or section of the RUFAS model. Examples: Animal, Feed Storage, Crop & Soil.

  • Expected Results - the set of results for a particular domain that should match your actual results when you run an end-to-end test on that domain. These are stored in the Filter File.

  • Actual Results - the set of results generated from an end-to-end testing run. An Actual Results file is generated for each domain each time you run end-to-end testing.

  • Filter File - a file containing the filters that were used to collect the expected AND actual results for a particular domain. This file contains:

    • The domain name

    • The filters used to collect expected and actual results

    • The set of expected results from those filters

    • The date of the last time these expected results were updated

  • Results File - a file containing the outcome of running end-to-end testing on a particular domain. This file contains:

    • The outcome of the test (passing or failing)

    • Any differences found between the actual and expected results

    • A results file is generated for each domain each time you run end-to-end testing

  • Must-Change Variables - Variables whose actual values are required to differ from their expected values for the end-to-end test to pass. These are typically used to verify that an intentional change to the model produces a change in the affected variables. See Must-Change Variables.

  • Accepted Ranges - A minimum and maximum allowable value for a variable. During end-to-end testing, the variable’s actual values are checked against this range rather than compared to the values in the expected results. The variable passes if all of its actual values fall within the accepted range, regardless of whether they match the expected results. See Accepted Ranges.

Why#

E2E testing will help prevent RuFaS outputs from changing in drastic or unexpected ways as changes are made to the code.

How#

As of 08/08/2025, E2E testing can only be run with dedicated sets of inputs. Run E2E testing with the following command:

python main.py -p input/metadata/end_to_end_testing_tm_metadata.json

There are three sets of inputs set up:

  1. Free Stall Dairy

    1. E2E testing is performed on the Crop&Soil, the Animal, and the Manure domain (module) of RuFaS.

    2. The simulation time period for the Free Stall E2E is cut short to only one year.

  2. Open Lot

    1. E2E testing is performed on the Crop&Soil, the Animal, and the Manure domain (module) of RuFaS.

    2. The simulation time period for the Open Lot E2E is cut short to only one year.

  3. No Animals

    1. No animals are simulated in this simulation. It is mainly used to verify the stand-alone C&S domain results.

    2. E2E testing is performed on the Crop&Soil and the Manure domain (module) of RuFaS.

For Each E2E test run:

  • A domain’s E2E test passes if there are no differences between the expected and actual results.

  • A domain’s E2E test fails if there are any differences.

  • Variables in the must-change list or with an accepted range are evaluated using different passing criteria. See Must-Change Variables and Accepted Ranges.

  • If an E2E test passes, the result is logged normally. If it fails, the result is logged as an error.

Output File Details#

For each domain, an output file will be generated with the E2E results. The file name includes the domain name and is labeled with a timestamp.

Example:

end-to-end-testing_saved_variables_feed_storage_e2e_results_16-Oct-2024_Wed_17-21-06.json

This output file contains:

  • Differences between actual and expected results: Details of variables whose actual values differ from their expected values.

  • end_to_end_testing_passing: A boolean value indicating whether the E2E test passed or not.

  • changed_variables: The names of variables whose actual values differ from their expected values. Variables designated as must-change or assigned an accepted range are excluded from this list because they are evaluated using separate passing criteria.

  • must_change_satisfied: The names of must-change variables whose actual values differ from their expected values, satisfying the requirement that they change.

  • must_change_violations: The must-change variables whose actual values did not change beyond the tolerance or that are missing from the actual results, each with the reason it failed.

  • accepted_range_satisfied: The variables whose actual values all fall within their accepted ranges, each with its range and the smallest and largest values found.

  • accepted_range_violations: The variables with an accepted range that have values outside the range, have no numerical values, or are missing from the actual results, each with its range and the reason it failed.

The must_change_* keys appear only if the domain has must-change variables, and the accepted_range_* keys only if it has variables with an accepted range. Each key starts with the domain name, for example Animal.changed_variables.

Must-Change Variables and Accepted Ranges#

By default, each variable’s actual value is compared against its expected value to determine whether it passes the end-to-end (E2E) comparison. Two optional configuration files allow different passing criteria to be specified for individual variables:

  • Must-change variables: Identifies variables whose actual values must differ from their expected values to pass the E2E comparison.

  • Accepted ranges: Defines minimum and maximum allowable values for variables. These variables pass if their actual values fall within the specified ranges, rather than being compared against their expected values.

Both configuration files are located in the corresponding input set’s directory under input/data/end_to_end_testing. For example, the freestall input set uses:

  • input/data/end_to_end_testing/freestall/freestall_must_change_variables.json

  • input/data/end_to_end_testing/freestall/freestall_accepted_ranges.json

Each configuration file can specify variables across all domains within its input set. Variable names must match the keys used in the expected_results section of the corresponding E2E JSON filter files. For example:

AnimalModuleReporter.report_305_day_milk_yield.milk_305_day_yield_herd_mean

RuFaS locates these configuration files using the must_change_variables_path and accepted_ranges_path keys in end_to_end_testing_result_paths.json. See E2E Testing Results Paths File for more information.

Must-Change Variables#

Use the must-change variables configuration file when an intentional change to the model is expected to affect specific output variables. Variables listed in this file are required to differ from their expected values by more than the tolerance defined for their domain to pass the E2E comparison. If a listed variable’s actual value remains within the tolerance of its expected value, the domain fails the comparison.

{
    "description": "Names of variables that must differ from the expected results. Empty this list after updating the expected results.",
    "must_change_variables": [
        "AnimalModuleReporter.report_enteric_methane_emission.enteric_methane_emission_for_LAC_COW_PEN_3",
        "AnimalModuleReporter.report_manure_excretions.LAC_COW_PEN_3_manure_mass"
    ]
}

How to use it:

  1. Run E2E testing. The results file of each domain lists the variables that differ from the expected results under changed_variables.

  2. Review the differences and add any variables that are expected to change as a result of the intentional model modifications to the must_change_variables list.

  3. Run E2E testing again. Variables in the must-change list are evaluated against their expected values using the must-change passing criteria. Variables that differ beyond the domain’s tolerance satisfy the requirement, while those that do not cause the domain to fail. These variables are no longer included in changed_variables.

  4. After updating the expected results to reflect the intended model changes, clear the must_change_variables list. RuFaS does not clear this list automatically. Leaving variables in the list causes the next E2E test run to fail, because their actual values now match the updated expected results.

Interpreting the results:

The E2E results file reports the outcomes of must-change comparisons using two fields:

  • must_change_satisfied: Lists variables whose actual values differ from their expected values beyond the domain’s tolerance, satisfying the must-change requirement.

  • must_change_violations: Identifies variables that failed the must-change requirement and provides an explanation for each failure.

Example results:

{
    "Animal.must_change_satisfied": {
        "values": [
            [
                "AnimalModuleReporter.report_manure_excretions.LAC_COW_PEN_3_manure_mass"
            ]
        ]
    },
    "Animal.must_change_violations": {
        "values": [
            {
                "AnimalModuleReporter.report_305_day_milk_yield.milk_305_day_yield_l1_mean": "Flagged as must change but the value still matches the expected results within the tolerance."
            }
        ]
    }
}

Accepted Ranges#

Use the accepted ranges configuration file when a variable’s actual values should be evaluated against a defined range rather than compared to its expected values. For example, an accepted range may be based on scientifically established limits or values reported in the literature.

A variable with an accepted range passes the E2E comparison only if all of its actual values fall within the specified minimum and maximum bounds, regardless of whether they differ from the expected results.

Example configuration:

{
    "description": "Accepted 'min' and 'max' for each variable name. All values of a listed variable must fall within them.",
    "accepted_ranges": {
        "AnimalModuleReporter.report_305_day_milk_yield.milk_305_day_yield_herd_mean": {
            "min": 10000,
            "max": 13000
        }
    }
}

Accepted range requirements:

  • Both min and max are required and must be numeric values, with min less than or equal to max.

  • The minimum and maximum bounds are inclusive, meaning values equal to either bound are considered passing.

  • Every numeric value recorded for a variable is evaluated against the specified range. For daily variables, this includes the value recorded for each day. For variables containing multiple numeric fields, the same range is applied to every field.

Enabling or disabling accepted ranges:

Accepted range validation is controlled by the use_accepted_ranges setting in input/data/tasks/end_to_end_testing_task.json. This setting is configured for each E2E task and defaults to true.

When use_accepted_ranges is set to false, the accepted ranges configuration file is not read, and variables are evaluated using the standard E2E comparison criteria unless another configured rule applies.

Interpreting the results:

The E2E results file reports accepted range comparisons using two fields:

  • accepted_range_satisfied: Identifies variables for which all recorded values fall within their accepted ranges.

  • accepted_range_violations: Identifies variables with one or more values outside their accepted ranges, with no numerical values, or missing from the actual results, and provides an explanation of each violation.

Both fields include the configured minimum and maximum bounds (min and max). They also include the smallest and largest values observed during the simulation (observed_min and observed_max), except for a variable that is missing or has no numerical values.

For violations, the reason field describes why the variable failed: how many recorded values fall outside the accepted range, or that the variable is missing or has no numerical values.

Example violation:

{
    "Animal.accepted_range_violations": {
        "values": [
            {
                "AnimalModuleReporter.report_manure_excretions.LAC_COW_PEN_3_urine": {
                    "min": 0,
                    "max": 1500,
                    "observed_min": 1244.110055144196,
                    "observed_max": 1748.8818365567322,
                    "reason": "191 of 366 values fall outside the accepted range."
                }
            }
        ]
    }
}

Things to keep in mind:

  • The tolerance is the tolerance set for the domain in end_to_end_testing_result_paths.json.

  • A variable in either file is left out of the normal comparison.

  • If use_accepted_ranges is false, the ranges are ignored. A variable with a range then gets the normal comparison, or only the must-change check if it is also in the must-change file.

  • A domain passes only if all of its variables pass.

  • A listed variable that is missing from the actual results fails.

  • A variable with an accepted range that has no numbers to check fails.

  • A name that is not in the expected results of any domain of the input set is a configuration error. So is a file that cannot be found or read, and a range without a valid min and max. RuFaS logs the error and does not compare any domain of that input set. This is checked after the simulation has run.

Setting up E2E Testing#

Quick Setup#

Note: E2E Testing is already ready to running on multiple domains for three sets of inputs. This section is for creating testing for a new sets of inputs, or setting up testing for an uncovered domain in an exisiting set of inputs.

New Input Set Setup#

In the input/data/end_to_end_testing directory:

  1. Create a folder with its name being the name for the new input set.

  2. Go into the folder, and create the 2 necessary E2E filter files following these formats: - E2E JSON Filter File

    • File name format: e2e_json_{domain}_filter.json.

    • See E2E JSON filter file. for reference.

    • Note: You won’t have anything to put in the expected_results section at setup time. This is expected. Keep following the steps.

    • E2E Comparison Filter

      • File name format: e2e_comparison_{domain}_differences.json.

      • See E2E Comparison filter file for reference.

    • Must-Change Variables and Accepted Ranges Files (optional)

      • File name formats: {input set}_must_change_variables.json and {input set}_accepted_ranges.json. Keep these endings. RuFaS uses them to tell these files apart from the filter files.

      • Copy the two files from an existing input set. They start empty.

      • See Must-Change Variables and Accepted Ranges for reference.

  3. Update the ``end_to_end_testing_task.json`` file in the input/data/tasks directory: - Use the existing entries as examples., create a new object in the "tasks" array, specifying:

    • “task_type”: “END_TO_END_TESTING”

    • “metadata_file_path”: the file path to the new input set metadata.

    • “output_prefix”: a custom output prefix for the new set of inputs, preferably following the patter {custom_name}_e2e. Please NOTE DOWN this output prefix name, it will be referenced later.

    • “filters_directory”: the directory path to the new directory conataining the two newly created filters.

    • “use_accepted_ranges”: true to check variables against the accepted ranges file, false to ignore that file.

    • “log_verbosity”: the desired verbosity, the suggested verbosity is “logs” for an E2E testing run.

    • “exclude_info_maps”: true. Please set this flag to true to exclude the info maps in the outputs, so that we can decrease the output file size and speed up the comparison process.

    • “random_seed”: the choice of random seed, default is set to 42.

  4. Update the ``update_end_to_end_testing_expected_results.json`` file in the input/data/tasks directory: - Use the existing entries as examples., create a new object in the "tasks" array, specifying:

    • “task_type”: “UPDATE_E2E_TEST_RESULTS”

    • “metadata_file_path”: the file path to the new input set metadata.

    • “output_prefix”: the same output prefix from end_to_end_testing_task.json.

    • “filters_directory”: the directory path to the new directory conataining the two newly created filters.

    • “log_verbosity”: the desired verbosity, the suggested verbosity is “logs” for a update E2E results run.

    • “exclude_info_maps”: true. Please set this flag to true to exclude the info maps in the outputs, so that we can decrease the output file size and speed up the comparison process.

    • “random_seed”: the choice of random seed, default is set to 42.

  5. Update the ``end_to_end_testing_results_paths.json`` file in the input/data/end_to_end_testing directory:

    • Create a new key-value pair in the “end_to_end_test_result_paths” dictionary. The key should be the output prefix specified in step 3 and 4.

    • Specify the domains you’re testing, the path to the expected outputs, and the pattern used to find the actual outputs for the domain module.

    • If you created the must-change variables and accepted ranges files in step 2, add their paths with the must_change_variables_path and accepted_ranges_path keys.

    • Use the existing entries as examples.

    • See E2E Testing Results Paths File for reference.

    • Note: You will not create a new results paths file. Add your new domain’s paths to the existing file.

  6. Update the ``default.json`` file in the input/data/metadata/properties directory:

    • Navigate to the “end_to_end_test_result_paths” block under the end_to_end_test_result_path_properties” section.

    • Create a new entry in the “end_to_end_test_result_paths” dictionary by copying and pasting one of the existing input set, with the key being the output prefix specified in step 3 and 4. For example, copy the entire “freestall_e2e” dictionary, paste it as a new entry, and change the key to the output prefix.

  7. Run the following command:

    python main.py -p input/metadata/update_end_to_end_testing_tm_metadata.json -c

    • This runs a simulation and updates the existing expected results with the new actual results for each domain.

    • If differences are found between the existing expected results and the new actual results, this will be logged for reference.

    • Monitor the logs for updates. If any unexpected domains show differences, STOP and investigate by comparing the expected and actual results.

    • Open each updated filter file and remove the automatically added top line to ensure there is human-in-the-loop (HIL) validation.

    • Contact a member of the dev team if you have questions or need assistance.

  8. Run the E2E testing command:

python main.py -p input/metadata/end_to_end_testing_tm_metadata.json

  1. Confirm your domain E2E test passes. If the test doesn’t pass, review steps 1–4 or contact a member of the RuFaS maintainer team for help.

New Domain Setup#

  1. Navigate to the corresponding folder for the input set you want to update in input/data/end_to_end_testing directory.**Create the 2 necessary E2E filter files** for the new domain by following step 2 from the New Input Set Setup section.

  2. Update the ``end_to_end_testing_results_paths.json`` file in the input/data/end_to_end_testing directory:

    • Navigate to the dictionary about the input set you want to update in the “end_to_end_test_result_paths” dictionary.

    • Use the existing entries as examples to add the filter files of the new domain.

  3. Follow steps 7-9 from the New Input Set Setup section to update the expected E2E results and confirm all E2E tests are successful.

Automatically Updating E2E Results#

As noted in step 3 of the Quick Setup instructions, you can run this command python main.py -p input/metadata/update_end_to_end_testing_tm_metadata.json -c to automatically update end-to-end-testing “expected results” for all domains of all input sets. These expected results are the results against which end-to-end testing will be run.

This is a powerful tool which removes some of the steps in updating the expected results by hand. However, there are still some safeguards against total automation to ensure expected results aren’t being unknowingly updated when this is run.

How does it work?

  1. For each input set, a simulation is run and output is filtered based on the filters in the existing E2E testing filters files.

  2. For each domain, the filtered results generated from that simulation are checked against the existing expected results for that domain.

  3. If any differences are found, it will automatically update the expected results in the appropriate filter file to reflect the actual results from the simulation that was just run. It will also update the expected_results_last_updated date in that filter file to reflect when the update occurred.

  4. Any updated filter file will also have this line of text printed across the top // WARNING: This is an autogenerated file. Remove this line for valid JSON.. This will cause the filter file to be invalid until a human user goes in, checks that the file looks correct, and removes this line. It is a safeguard against accidental updates to these files.

It is always good practice after running this automatic update to re-run end-to-end testing to ensure that the results were properly updated.

The update does not read or change the must-change variables and accepted ranges files. If the must-change list of an input set is not empty, empty it before you re-run end-to-end testing. See Must-Change Variables.

More Detailed Setup Explanation#

When E2E testing runs, special filter files are needed to properly collect the actual and expected results. These filters are very similar to regular RuFaS filters, but are prefixed with e2e_ (see the full list of supported E2E filter prefixes here).

There are only two supported filter types currently:

  1. JSON (e2e_json_)

  2. Comparison (e2e_comparison_)

The E2E JSON filters are almost identical to regular JSON filters, with one major difference:. E2E JSON filters contain a key called “expected_results”, which points to the results that are expected to be collected from RuFaS with the patterns pointed to by the “filters” key.

The comparison filter files are regular JSON filter files that only contain one pattern, used to collect the differences between the actual and expected results for a single domain.

These filter file types were introduced because JSON filter files should only be used in the first post-processing that RuFaS executes, and comparison files only in the second post-processing.

In order for the actual and expected results to be connected, RuFaS uses the file input/data/end_to_end_testing/end_to_end_testing_result_paths.json. This file should contain:

  • a dictionay of a list of objects, each item in the dictionary represents an input set , and each object whitn the

    list contains the name of the RuFaS domain being tested.

  • the path to the expected results (which is the path to the filter file for that domain located within the end_to_end_testing directory).

  • a pattern used to identify the actual results.

Two important points:

  1. The file containing the actual results is produced as RuFaS filters with the patterns listed in the expected results file, so it is critical that the “name” field of that file matches what is in the actual results path.

  2. The filter in the comparison file must match the domain that is listed in the end_to_end_testing_result_paths.json file, otherwise the comparison file will not be able to correctly filter out the results of E2E testing.

Example Files#

Example files are provided to illustrate the description of how E2E filter files are structured.

E2E JSON filter file.#

This is the filter file for testing the Feed Storage module (e2e_json_feed_storage_filter.json), which contains both filters and expected results:

{
    "name": "e2e_feed_storage",
    "filters": [
        "Weather.*",
        "Time.*",
        "ProtectedIndoors.*",
        "ProtectedWrapped.*",
        "ProtectedTarped.*",
        "Unprotected.*",
        "Baleage.*",
        "Dry.*",
        "HighMoisture.*",
        "Bunker.*",
        "Pile.*",
        "Bag.*"
    ],
    "expected_results": {
        "DISCLAIMER": "Under construction, use the results with caution.",
        "Weather.average_annual_temperature": {
            "info_maps": [
            {
                "prefix": "Weather",
                "units": "\u00b0C"
            }
            ],
            "values": [
            8.178051643192488
            ]
        },
        ...
    }
}

Like a regular filter file, it has both a “name” and “filters” entry which RuFaS uses to filter the OutputManager’s pool. But unlike regular filter files, there is a key called “expected_results”, which contains all the data that is expected to be collected with the filters listed in this file.

E2E Comparison filter file.#

This is the filter file for collecting the E2E test results for Feed Storage, e2e_comparison_feed_storage_differences.json.

{
    "name": "feed_storage_e2e_results",
    "filters": ["FeedStorage.*"]
}

Because the file name of this filter is prefixed with “e2e_comparison_”, this filter file will only be after RuFaS has finished comparing the actual and expected results from the filter file listed above.

E2E Testing Results Paths File.#

The results filter and the comparison filters have to be linked so that RuFaS is able to find the correct files for the actual and expected results, and record their differences so that they can be collected properly. This is accomplished in the end_to_end_testing_result_paths.json.

{
    "end_to_end_test_result_paths": {
     "freestall_e2e": [
            {
                "domain": "FeedStorage",
                "expected_results_path": "input/data/end_to_end_testing/e2e_json_feed_storage_filter.json",
                "actual_results_path": "end-to-end-testing_saved_variables_e2e_feed_storage_",
                "tolerance": 0.1,
                "must_change_variables_path": "input/data/end_to_end_testing/freestall/freestall_must_change_variables.json",
                "accepted_ranges_path": "input/data/end_to_end_testing/freestall/freestall_accepted_ranges.json"
            }
        ]
     }
}

The “expected_results_path” points to the filter file which contains the expected results, and the “actual_results_path” entry contains the pattern that will start the file produced by the filter file containing the expected results. The “tolerance” is the percent tolerance allowed between the expected and actual results. It can be set individually for each domain to be more or less lenient.

The “must_change_variables_path” and “accepted_ranges_path” entries are optional. They point to the must-change variables file and the accepted ranges file of the input set. All the domains of an input set point to the same two files. See Must-Change Variables and Accepted Ranges.

Some important things to note in the “actual_results_path”:

  • It starts with “end-to-end-testing”, this must match the output prefix of the task that is running E2E testing.

  • It ends with “e2e_feed_storage”, this must match the “name” key in the filter file which contains the expected results.

  • The pattern is not a full file name, it is only the beginning. The full file name with the actual results will contain a timestamp, but this is not known when this entry is written so the pattern can only match the start of the file. It is important that the results from the last E2E test run are cleared before re-running E2E testing, otherwise it is not ensured that RuFaS will find the actual results from the last E2E test run.

It is also critical that the “domain” entry matches the pattern in the Feed Storage comparison file. RuFaS uses the domain entry as the prefix when it records E2E test results as variables to the Output Manager, so if the pattern does not match the domain name then the results for the E2E test will not be collected properly by the comparison file.
